Câu 1.1: Luồng phân giải tên miền DNS (DNS Resolution) hoạt động như thế nào? Phân biệt các bản ghi A, AAAA, CNAME, MX, TXT, NS? Domain & DNS
  • Luồng phân giải DNS (Khi gõ api.example.com):
    1. Browser Cache & OS Cache: Trình duyệt kiểm tra bộ nhớ đệm DNS của nó và file /etc/hosts + OS DNS cache.
    2. Recursive Resolver (ISP hoặc 1.1.1.1 / 8.8.8.8): Nếu cache miss, máy tính hỏi DNS Resolver.
    3. Root Nameserver (.) ➡️ TLD Nameserver (.com) ➡️ Authoritative Nameserver (Cloudflare/Route53): Resolver đi hỏi tuần tự từ gốc đến máy chủ quản lý tên miền chính thức để lấy địa chỉ IP (vd: 104.21.55.12) và lưu cache theo thời gian TTL.
  • Phân biệt các loại DNS Record quan trọng nhất:
    • A Record: Ánh xạ tên miền (Domain/Subdomain) tới địa chỉ IPv4 (vd: example.com -> 103.22.11.5).
    • AAAA Record: Ánh xạ tên miền tới địa chỉ IPv6.
    • CNAME (Canonical Name): Ánh xạ một tên miền phụ (alias) sang một tên miền khác (vd: www.example.com -> example.com hoặc trỏ vào myapp.onrender.com).
    • MX (Mail Exchange): Chỉ định máy chủ nhận email cho tên miền kèm độ ưu tiên (priority).
    • TXT Record: Lưu chuỗi văn bản dùng để xác minh quyền sở hữu tên miền (Google Search Console) hoặc bảo mật chống giả mạo email (SPF, DKIM, DMARC).
    • NS (Nameserver): Chỉ định đơn vị nào có quyền quản lý bản ghi DNS của domain (vd: ns1.cloudflare.com).
🪤 Bẫy phỏng vấn DNS: "Có thể tạo bản ghi CNAME cho Root Domain (example.com / @) được không?"
➡️ Trả lời: Theo chuẩn RFC 1034, KHÔNG THỂ dùng CNAME chuẩn ở Root Domain (Zone Apex @) vì CNAME không được phép tồn tại chung với bất kỳ bản ghi nào khác (như NS và SOA bắt buộc phải có ở root). Để khắc phục, Cloudflare/Route53 cung cấp CNAME Flattening hoặc ALIAS / ANAME record.
Câu 1.2: Tại sao Nginx lại xử lý được hàng chục nghìn kết nối đồng thời (Bài toán C10K) với lượng RAM cực thấp so với Apache? Nginx Architecture
  • Apache truyền thống (Process / Thread-driven): Mỗi kết nối mạng tạo một OS Process hoặc Thread riêng biệt. Khi có 10,000 kết nối đồng thời (đặc biệt các kết nối mạng chậm hoặc Keep-Alive), 10,000 threads ngốn hàng chục GB RAM và làm CPU kiệt sức vì Context Switching.
  • Nginx (Master-Worker + Event-Driven Asynchronous Non-blocking):
    • 1 Master Process: Chạy với quyền root để đọc/validate file config, bind cổng 80/443 và quản lý các Worker.
    • N Worker Processes (thường cấu hình worker_processes auto; = số nhân CPU): Mỗi Worker là Single-Threaded nhưng sử dụng cơ chế I/O Multiplexing (epoll trên Linux / kqueue trên macOS/BSD).
    • Một Worker duy nhất có thể giữ 10,000+ kết nối đồng thời trong một vòng lặp sự kiện (Event Loop). Khi kết nối đang chờ I/O từ Backend hoặc Client, Worker không hề bị block mà lập tức phục vụ request khác.
Câu 1.3: Phân biệt Forward Proxy vs Reverse Proxy? Layer 4 vs Layer 7 Load Balancing? Các thuật toán Load Balancing trong Nginx? Reverse Proxy & LB
Tiêu chí Forward Proxy (Squid, VPN) Reverse Proxy (Nginx, HAProxy, Envoy)
Đứng đại diện cho ai? Đứng trước Client (đại diện cho người dùng đi ra Internet). Đứng trước Backend Servers (đại diện cho hệ thống server nhận request từ Internet).
Ai bị ẩn danh? Server ngoài Internet không biết IP thật của Client. Client bên ngoài không biết IP nội bộ và cấu trúc các Backend Servers phía sau.
Công dụng chính Kiểm soát truy cập mạng công ty, caching nội bộ, vượt tường lửa. Load Balancing, SSL Termination, nén Gzip/Brotli, Rate Limiting, phục vụ Static Files, bảo vệ Backend.
  • Layer 4 (Transport - TCP/UDP) vs Layer 7 (Application - HTTP/HTTPS) Load Balancing:
    • Layer 4 (stream {} trong Nginx): Chỉ nhìn thấy IP + Port. Chuyển tiếp gói tin TCP/UDP siêu tốc mà không cần giải mã HTTP. Dùng cho Database Proxy (PostgreSQL/MySQL), Redis, MQTT, Game Server.
    • Layer 7 (http {} trong Nginx): Giải mã SSL và đọc toàn bộ nội dung HTTP (Host, URI path, Header, Cookie). Cho phép định tuyến thông minh: /api/v1/ vào Node.js, /ai/ vào Python FastAPI, /static/ đọc từ ổ cứng.
  • 4 Thuật toán Load Balancing trong khối upstream của Nginx:
    1. Round Robin (Mặc định): Chia đều request xoay vòng tuần tự qua các server.
    2. Least Connections (least_conn;): Chuyển request mới vào server đang có ít kết nối active nhất (rất tốt khi thời gian xử lý mỗi request dài ngắn khác nhau).
    3. IP Hash (ip_hash;): Băm địa chỉ IP của Client để luôn định tuyến cùng 1 khách hàng vào cùng 1 server (Sticky Session).
    4. Weighted (weight=3;): Chia tải theo tỷ lệ cấu hình phần cứng của từng server.
Câu 1.4: Phân biệt các mã lỗi kinh điển trên Nginx: 502 Bad Gateway, 503 Service Unavailable, 504 Gateway Timeout, 413 Content Too Large, 499 Client Closed Request? Production Troubleshooting
Mã lỗi HTTP Bản chất xảy ra tại Nginx Nguyên nhân thực tế & Cách khắc phục
502 Bad Gateway Nginx không thể mở kết nối TCP tới Backend Upstream hoặc nhận phản hồi rác. Process Backend (Node.js/Gunicorn/PHP-FPM) bị crash/tắt, cấu hình sai port trong proxy_pass, hoặc cạn kiệt file descriptors/socket. ➡️ Kiểm tra systemctl status app / docker ps.
503 Service Unavailable Nginx chủ động từ chối phục vụ do quá tải hoặc bảo trì. Client gửi quá nhanh bị chặn bởi limit_req / limit_conn trên Nginx, hoặc tất cả node trong upstream đều bị đánh dấu down.
504 Gateway Timeout Nginx đã gửi request xuống Backend nhưng chờ quá hạn mà Backend chưa trả lời. Backend bị treo vì câu query DB chậm, deadlock, hoặc gọi API bên thứ 3 không đặt timeout (vượt quá proxy_read_timeout 60s;). ➡️ Tối ưu DB/chuyển sang Background Job (Celery/BullMQ).
413 Payload Too Large User upload file vượt quá giới hạn body mặc định của Nginx (mặc định chỉ 1MB!). Thêm chỉ thị client_max_body_size 100M; vào khối http hoặc server trong nginx.conf, hoặc dùng Presigned URL upload thẳng lên S3.
499 Client Closed Request Mã lỗi riêng của Nginx: Client tự ngắt kết nối (đóng tab hoặc FE timeout) trước khi Backend kịp trả kết quả. Thường do Axios/Fetch ở FE đặt timeout 5s nhưng API Backend mất 8s mới chạy xong.
Câu 1.5: Sự khác biệt giữa root và alias trong Nginx? Thứ tự ưu tiên của khối location? Mẫu file nginx.conf chuẩn Production? Config Thực Chiến
  • Phân biệt root vs alias khi phục vụ file tĩnh (Rất hay hỏi khi fix lỗi 404 Static Files):
    • location /static/ { root /var/www/app; } ➡️ Nginx lấy root CỘNG THÊM toàn bộ URI /static/... ➡️ Tìm file tại: /var/www/app/static/logo.png.
    • location /static/ { alias /var/www/app/staticfiles/; } ➡️ Nginx THAY THẾ chữ /static/ bằng đường dẫn alias ➡️ Tìm file tại: /var/www/app/staticfiles/logo.png.
  • Thứ tự ưu tiên khớp location trong Nginx (Từ cao xuống thấp):
    1. location = /login — Khớp chính xác 100% (Exact match, dừng tìm kiếm ngay).
    2. location ^~ /static/ — Khớp tiền tố ưu tiên cao (Preferential prefix, nếu khớp sẽ bỏ qua Regex).
    3. location ~ \.php$ hoặc ~* \.(jpg|png)$ — Khớp biểu thức chính quy (Regex, ưu tiên theo thứ tự xuất hiện từ trên xuống dưới trong file).
    4. location /api/ — Khớp tiền tố dài nhất (Longest prefix match).
    5. location / — Fallback mặc định cho mọi request còn lại.

    2. Đẩy sang Background Job Queue (BullMQ / Redis / RabbitMQ / Google Pub/Sub): API chỉ nhận request, đẩy job vào Queue và trả về 202 Accepted (jobId) ngay lập tức; các Worker process riêng biệt phía sau sẽ xử lý.
    3. Dùng Cluster Module / PM2 Cluster Mode: Chạy nhiều Node.js processes trên tất cả các nhân CPU để một process bận không làm tịt toàn bộ máy chủ.
    4. Tách sang Service chuyên dụng (Go / Rust / Python): Với AI inference, xử lý video/ảnh nặng, tách riêng thành worker viết bằng ngôn ngữ tối ưu cho CPU.

3) Image có bị build sai kiến trúc CPU không (build trên Mac M1/M2 arm64 nhưng Cloud Run yêu cầu linux/amd64 ➡️ phải build với docker build --platform linux/amd64)!
8 Pub/Sub đảm bảo exactly-once hay at-least-once? Mặc định trên toàn hệ thống là at-least-once (đảm bảo không mất tin nhưng có thể lặp). Hiện tại Pub/Sub có hỗ trợ cấu hình Exactly-once delivery cho Pull Subscription trong cùng region, nhưng ở tầng ứng dụng Backend chuẩn thực chiến vẫn luôn phải viết logic Idempotent Consumer.
9 Vì sao nên dùng Service Account riêng cho từng service? Tuân thủ nguyên tắc Least Privilege (Đặc quyền tối thiểu) và Blast Radius Isolation: nếu Worker gửi Email chỉ cần quyền đọc Pub/Sub mà bị lộ lỗ hổng, hacker cũng không thể xóa bảng Cloud SQL hay đọc bucket Cloud Storage của các service khác. Đồng thời giúp truy vết Cloud Audit Logs biết chính xác service nào vừa gọi API gì.
10 Làm sao Rollback một bản deploy lỗi trên Cloud Run? Mỗi lần deploy Cloud Run tạo một Revision bất biến (Immutable Revision). Khi bản mới bị lỗi, chỉ mất 5 giây trên UI hoặc lệnh CLI gcloud run services update-traffic my-service --to-revisions=my-service-00012=100 để chuyển 100% traffic về Revision cũ mà không cần chờ build lại image. Ngoài ra có thể dùng Canary Traffic Splitting (chuyển thử 5% traffic vào bản mới trước).
11 Khi nào cần Dead Letter Topic (DLQ) trong Pub/Sub? Khi một message bị lỗi dữ liệu (Poison Pill — ví dụ JSON sai định dạng hoặc thiếu trường bắt buộc) khiến Worker xử lý lỗi liên tục. Nếu không có Dead Letter Topic (giới hạn max_delivery_attempts = 5), Pub/Sub sẽ giữ và bắn lại message đó suốt nhiều ngày gây nghẽn hàng đợi và tốn chi phí. DLQ giúp tách message lỗi ra để cảnh báo và kiểm tra sau.
12 Các Metric quan trọng nhất của API Serverless là gì? Theo 4 Golden Signals của Google SRE: 1) Latency (độ trễ phân vị p50, p95, p99); 2) Traffic (Request count / RPS); 3) Errors (Tỷ lệ lỗi HTTP 5xx, 4xx, container crash); 4) Saturation (CPU/Memory utilization, Container Instance Count, Cold Start latency, và Pub/Sub num_undelivered_messages / Oldest unacked message age).
13 Vì sao max-instances cực kỳ quan trọng khi Cloud Run kết nối Cloud SQL? PostgreSQL/MySQL có giới hạn số kết nối tối đa (vd: max_connections = 100). Nếu không giới hạn max-instances, khi traffic tăng đột biến Cloud Run tự động bật lên 100 instances $\times$ mỗi instance mở pool 5 connections = 500 connections ➡️ Làm sập hoàn toàn Cloud SQL (FATAL: remaining connection slots are reserved)! Cần đặt max-instances hợp lý và dùng PgBouncer hoặc giới hạn pool size.
14 Cloud Scheduler có thể trigger những gì? Cloud Scheduler (Managed Cron Job) có thể kích hoạt trực tiếp 3 loại đích theo lịch trình Cron: 1) HTTP/HTTPS Endpoint (gọi API Cloud Run, Cloud Functions, Cloud Run Jobs hoặc webhook kèm OIDC/OAuth token); 2) Pub/Sub Topic (bắn bản tin định kỳ vào hàng đợi); 3) App Engine HTTP target.
15 Làm sao Trace lỗi đi qua nhiều Microservices trên GCP? Ngay tại API Gateway / Service đầu tiên, sinh một correlationId / traceId (hoặc đọc header chuẩn của GCP là X-Cloud-Trace-Context / chuẩn W3C traceparent). Truyền ID này xuyên suốt qua HTTP Header và Pub/Sub Message Attributes. Mọi service khi ghi Structured JSON Log đều đính kèm trường traceId, giúp gõ 1 lệnh trên Cloud Logging / Cloud Trace là thấy toàn bộ hành trình của request qua 5 services.
