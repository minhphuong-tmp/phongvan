Câu 1 Junior Node.js Basics

What is Node.js and why is it used?

🇻🇳 Node.js là gì và tại sao lại được sử dụng rộng rãi?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Node.js là một runtime environment mã nguồn mở, đa nền tảng, chạy JavaScript phía server dựa trên V8 JavaScript Engine của Google Chrome. Node.js sử dụng mô hình I/O phi chặn (non-blocking), hướng sự kiện (event-driven), giúp xây dựng các ứng dụng mạng có khả năng mở rộng cao và xử lý đồng thời hàng nghìn kết nối với tài nguyên bộ nhớ tối thiểu.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Kiến trúc cốt lõi: Kết hợp giữa V8 Engine (biên dịch JS sang mã máy C++) và thư viện libuv (xử lý Event Loop, Thread Pool cho các tác vụ I/O bất đồng bộ).
2. Single-Threaded Event Loop: Xử lý request trên 1 luồng chính duy nhất, đẩy các tác vụ nặng (file I/O, network DNS, crypto) sang libuv worker pool (mặc định 4 threads).
3. Trường hợp sử dụng tối ưu: Các ứng dụng I/O-heavy như Chat realtime, RESTful API, Streaming data, Single Page App backends, Microservices. Không tối ưu cho tác vụ CPU-intensive (xử lý video, tính toán ma trận) nếu không dùng Worker Threads.
💻 Code Ví Dụ Minh Họa & Output 
const http = require('http');

// Tạo HTTP Server bất đồng bộ xử lý non-blocking I/O
const server = http.createServer((req, res) => {
  res.writeHead(200, { 'Content-Type': 'application/json' });
  res.end(JSON.stringify({
    status: 'success',
    message: 'Hello from Node.js Event-Driven Architecture!',
    timestamp: new Date().toISOString()
  }));
});

const PORT = 3000;
server.listen(PORT, () => {
  console.log(`Server running at http://localhost:${PORT}/`);
});
💡 Điểm Cộng & Bẫy Phỏng Vấn (Gotchas / Senior Tips)
Điểm cộng lớn khi phỏng vấn: Đừng chỉ nói 'Node.js là single-threaded'. Hãy giải thích rõ ràng rằng JavaScript code chạy single-threaded trên main event loop, nhưng bản thân Node.js bên dưới là multi-threaded nhờ libuv C++ thread pool.
Câu 2 Mid Node.js Basics

How does Node.js handle child threads?

🇻🇳 Node.js xử lý Child Threads và đa luồng như thế nào?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Node.js xử lý đa luồng thông qua nhiều cơ chế: (1) libuv Thread Pool ngầm bên dưới cho I/O, (2) module child_process để fork/spawn tiến trình độc lập, và (3) module worker_threads (từ Node v10.5+) cho phép tạo các luồng thực sự chia sẻ chung bộ nhớ qua SharedArrayBuffer.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. libuv Worker Pool: Mặc định có 4 threads (có thể cấu hình qua biến môi trường UV_THREADPOOL_SIZE=n), phục vụ fs, crypto, zlib, dns.lookup.
2. child_process: (spawn, exec, fork) tạo ra OS process mới riêng biệt với memory space riêng, giao tiếp qua IPC channel.
3. worker_threads: Chạy song song nhiều V8 isolate trên cùng một tiến trình, tiết kiệm RAM hơn fork, thích hợp tuyệt đối cho tính toán CPU-heavy (mã hóa, nén ảnh, xử lý dữ liệu lớn).
💻 Code Ví Dụ Minh Họa & Output 
// main.js - Sử dụng worker_threads cho tác vụ tính toán nặng
const { Worker, isMainThread, parentPort, workerData } = require('worker_threads');

if (isMainThread) {
  // Main thread: không bị block, vẫn tiếp tục lắng nghe request
  const worker = new Worker(__filename, { workerData: { countTo: 1e8 } });
  
  worker.on('message', result => console.log('Worker hoàn thành:', result));
  worker.on('error', err => console.error('Worker lỗi:', err));
  console.log('Main thread vẫn chạy mượt mà, không bị lag!');
} else {
  // Worker thread: chạy trên CPU core riêng
  let sum = 0;
  for (let i = 0; i < workerData.countTo; i++) sum += i;
  parentPort.postMessage({ total: sum });
}
💡 Điểm Cộng & Bẫy Phỏng Vấn (Gotchas / Senior Tips)
Senior Tip: Phân biệt rõ khi nào dùng `cluster/child_process` (mỗi tiến trình 1 V8 riêng, cô lập hoàn toàn, dùng để scale app) và khi nào dùng `worker_threads` (chia sẻ bộ nhớ, dùng giải quyết bottleneck CPU).
Câu 3 Junior Node.js Basics

Describe the event-driven programming in Node.js.

🇻🇳 Mô hình lập trình hướng sự kiện (Event-Driven) trong Node.js hoạt động ra sao?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Lập trình hướng sự kiện là mô hình trong đó luồng điều khiển của ứng dụng được kích hoạt bởi các sự kiện (events) như click, I/O hoàn thành, kết nối socket mới, hay dữ liệu gửi đến qua stream. Đối tượng phát ra sự kiện (Event Emitter) và các hàm lắng nghe (Listeners/Handlers) sẽ phản hồi lại sự kiện đó.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Observer Pattern: Module `events` với class `EventEmitter` là xương sống của mọi module trong Node.js (http.Server, fs.ReadStream, socket, process đều kế thừa EventEmitter).
2. Quy trình: Khi một thao tác I/O hoàn thành, libuv gửi callback vào Event Loop queue, Event Loop kích hoạt listener tương ứng.
3. Đồng bộ vs Bất đồng bộ: Mặc định EventEmitter gọi các listener theo thứ tự ĐỒNG BỘ khi `emit()` được gọi, trừ khi bên trong listener dùng `setImmediate` hoặc `process.nextTick`.
💻 Code Ví Dụ Minh Họa & Output 
const EventEmitter = require('events');

class OrderService extends EventEmitter {}
const orderService = new OrderService();

// Đăng ký listener lắng nghe sự kiện 'orderPlaced'
orderService.on('orderPlaced', (order) => {
  console.log(`[Email] Đang gửi email xác nhận cho đơn hàng #${order.id}`);
});

orderService.on('orderPlaced', (order) => {
  console.log(`[Inventory] Trừ kho cho sản phẩm ${order.productId}`);
});

// Phát sự kiện (trigger)
console.log('Khách hàng bấm thanh toán...');
orderService.emit('orderPlaced', { id: 101, productId: 'MACBOOK-M3', price: 2000 });
💡 Điểm Cộng & Bẫy Phỏng Vấn (Gotchas / Senior Tips)
Lưu ý cảnh báo rò rỉ bộ nhớ: EventEmitter có giới hạn mặc định `defaultMaxListeners = 10`. Nếu bạn gắn quá 10 listeners mà không remove, Node.js sẽ in warning `MaxListenersExceededWarning` cảnh báo memory leak.
Câu 4 Senior Node.js Basics

What is the event loop in Node.js?

🇻🇳 Event Loop trong Node.js là gì và các giai đoạn (phases) của nó hoạt động như thế nào?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Event Loop là cơ chế liên tục kiểm tra và điều phối việc thực thi mã code, thu thập và xử lý các sự kiện, cũng như thực thi các tác vụ con trong hàng đợi callback. Event Loop giúp Node.js thực hiện các thao tác non-blocking I/O dù chỉ chạy trên 1 luồng JavaScript duy nhất.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
Event Loop của libuv gồm 6 pha (phases) lặp tuần tự:
1. Timers: Thực thi callback của `setTimeout()` và `setInterval()`.
2. Pending Callbacks: Xử lý I/O callbacks bị hoãn từ vòng lặp trước (ví dụ lỗi mạng TCP ECONNREFUSED).
3. Idle, Prepare: Dùng nội bộ bởi libuv.
4. Poll: Pha quan trọng nhất - tính toán thời gian block chờ I/O mới và xử lý các sự kiện I/O (ngoại trừ timers, close, setImmediate).
5. Check: Thực thi callback của `setImmediate()`.
6. Close Callbacks: Xử lý các sự kiện đóng, ví dụ `socket.on('close', ...)`.
* Chú ý Microtasks: `process.nextTick()` queue và Promise microtask queue được ưu tiên thực thi ngay lập tức sau mỗi tác vụ và giữa các giai đoạn!
💻 Code Ví Dụ Minh Họa & Output 
console.log('1. Đồng bộ (Start)');

setTimeout(() => console.log('5. Timers phase: setTimeout'), 0);
setImmediate(() => console.log('6. Check phase: setImmediate'));

Promise.resolve().then(() => console.log('3. Microtask: Promise.then'));
process.nextTick(() => console.log('2. Microtask ưu tiên cao nhất: process.nextTick'));

console.log('4. Đồng bộ (End)');

// Output chính xác:
// 1. Đồng bộ (Start)
// 4. Đồng bộ (End)
// 2. Microtask ưu tiên cao nhất: process.nextTick
// 3. Microtask: Promise.then
// 5. Timers phase: setTimeout (hoặc Check phase tùy context I/O)
// 6. Check phase: setImmediate
💡 Điểm Cộng & Bẫy Phỏng Vấn (Gotchas / Senior Tips)
Câu hỏi sát thủ Senior: 'Trong một I/O cycle (ví dụ trong fs.readFile), giữa setImmediate và setTimeout(..., 0), cái nào luôn chạy trước?' Đáp án: `setImmediate` luôn chạy trước vì sau khi I/O callback xong ở Poll phase, Event Loop chuyển ngay sang Check phase!
Câu 5 Mid Node.js Basics

What is the difference between Node.js and traditional web server technologies?

🇻🇳 Sự khác biệt giữa Node.js và các công nghệ máy chủ truyền thống (Apache, PHP, Java Servlets)?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Máy chủ truyền thống (như Apache/PHP đa luồng) áp dụng mô hình Thread-per-request: mỗi kết nối khách chiếm 1 thread riêng và bị block khi chờ I/O (Database, Disk). Trong khi đó, Node.js áp dụng kiến trúc Single-Threaded Event Loop kết hợp Non-blocking I/O: 1 thread duy nhất phục vụ hàng vạn kết nối đồng thời mà không bị block.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Tiêu tốn bộ nhớ: 1 thread trong Apache/Java tốn 1MB - 2MB stack RAM. 10,000 kết nối tốn 10GB-20GB RAM (gây crash hoặc swap disk - C10K problem). Node.js chỉ tốn vài chục bytes cho 1 socket descriptor.
2. Context Switching: Đa luồng truyền thống tốn chi phí CPU khổng lồ để chuyển đổi ngữ cảnh giữa hàng nghìn threads. Node.js không bị tốn chi phí context switch trên main loop.
3. Điểm yếu của Node.js: Nếu có 1 request thực hiện thuật toán nặng chiếm dụng CPU (như vòng lặp vô tận), toàn bộ người dùng khác sẽ bị đứng hình. Mô hình đa luồng truyền thống chỉ bị treo luồng của người đó.
💻 Code Ví Dụ Minh Họa & Output 
// Minh họa non-blocking trong Node.js:
// Hàng ngàn requests vào cùng lúc không ai phải chờ ai hoàn thành database query
const fs = require('fs');

console.time('Non-blocking');
fs.readFile(__filename, (err, data) => {
  console.log(`Đã đọc xong file (${data.length} bytes)`);
});
console.log('Server vẫn thoải mái phục vụ các requests khác ngay lập tức!');
console.timeEnd('Non-blocking');
💡 Điểm Cộng & Bẫy Phỏng Vấn (Gotchas / Senior Tips)
Khi so sánh, hãy dùng thuật ngữ C10K Problem và Context Switching Overhead. Đó là hai điểm mạnh cốt tử giúp Node.js chiến thắng các hệ thống cũ trong các bài toán web hiện đại.
Câu 6 Junior Node.js Basics

Explain what “non-blocking” means in Node.js.

🇻🇳 Khái niệm 'Non-blocking' (Phi chặn) trong Node.js nghĩa là gì?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
'Non-blocking' có nghĩa là các thao tác I/O (đọc ghi đĩa, truy vấn cơ sở dữ liệu, gọi API bên ngoài) không bắt CPU JavaScript phải dừng lại chờ đợi kết quả trả về. Thay vào đó, hàm sẽ ủy thác cho hệ điều hành/libuv thực thi ngầm và tiếp tục chạy ngay các dòng code tiếp theo.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Blocking I/O: `const data = fs.readFileSync('data.txt')` khiến toàn bộ tiến trình dừng lại cho đến khi đọc xong từng byte trên ổ cứng. Không request nào khác được phục vụ trong lúc này.
2. Non-blocking I/O: `fs.readFile('data.txt', callback)` trả về quyền điều khiển ngay lập tức. Libuv thực thi ngầm ở background, khi có dữ liệu thì đưa callback vào Event Loop queue.
3. Lợi ích: Tối ưu hóa tối đa thời gian nhàn rỗi (idle time) của CPU để đạt throughput cực lớn.
💻 Code Ví Dụ Minh Họa & Output 
const fs = require('fs');

console.log('--- 1. Bắt đầu tác vụ ---');

// Thao tác Non-blocking (Asynchronous)
fs.readFile(__filename, 'utf8', (err, content) => {
  if (err) throw err;
  console.log('--- 3. Đã đọc xong file bất đồng bộ ---');
});

console.log('--- 2. Dòng này chạy ngay lập tức mà không bị nghẽn! ---');
💡 Điểm Cộng & Bẫy Phỏng Vấn (Gotchas / Senior Tips)
Luôn tránh sử dụng các hàm có hậu tố `Sync` (như `readFileSync`, `writeFileSync`) trong route handlers của production server, vì chúng biến Node.js thành blocking single-thread gây treo toàn bộ ứng dụng.
Câu 7 Junior Node.js Basics

How do you update Node.js to the latest version?

🇻🇳 Cách cập nhật Node.js lên phiên bản mới nhất?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Cách chuẩn và chuyên nghiệp nhất trong môi trường phát triển là sử dụng công cụ quản lý phiên bản Node như nvm (Node Version Manager) hoặc fnm (Fast Node Manager). Trên production hoặc container, thường cập nhật phiên bản base image trong Dockerfile.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Với nvm (khuyên dùng):
- Cài bản mới nhất: `nvm install node`
- Cài bản LTS mới nhất (khuyến nghị cho production): `nvm install --lts`
- Chuyển phiên bản: `nvm use --lts`
- Đặt mặc định: `nvm alias default 'lts/*'`
2. Với Volta hoặc fnm: Quản lý tự động theo từng project thông qua cấu hình `engines` trong `package.json`.
3. Kiểm tra bảo mật: Trước khi nâng cấp, luôn kiểm tra Node.js Release Schedule và Changelog xem có breaking changes không.
💻 Code Ví Dụ Minh Họa & Output 
# Các lệnh thực thi trong Terminal:
nvm ls-remote --lts          # Xem danh sách các phiên bản LTS có sẵn
nvm install 20               # Cài đặt Node.js LTS v20
nvm use 20                   # Chuyển sang dùng v20
node -v                      # Kiểm tra phiên bản hiện tại (ví dụ: v20.12.0)
npm -v                       # Kiểm tra phiên bản npm đi kèm
💡 Điểm Cộng & Bẫy Phỏng Vấn (Gotchas / Senior Tips)
Luôn khuyên dùng phiên bản LTS (Long-Term Support) cho dự án doanh nghiệp để đảm bảo tính ổn định và bảo mật trong vòng 30 tháng.

What is “npm” and what is it used for?

🇻🇳 'npm' là gì và được sử dụng để làm gì?

How do you create a simple server in Node.js using the HTTP module?

🇻🇳 Cách tạo một HTTP Server cơ bản trong Node.js sử dụng core module `http`?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Sử dụng hàm http.createServer() truyền vào một callback nhận 2 tham số req (IncomingMessage - một Readable Stream) và res (ServerResponse - một Writable Stream), sau đó gọi server.listen(port) để bắt đầu lắng nghe kết nối.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Request Handling: `req` chứa thông tin method, url, headers. Để đọc body POST, ta phải lắng nghe sự kiện `'data'` và `'end'` vì dữ liệu được truyền dạng chunks.
2. Response Writing: Dùng `res.writeHead()` để set status code và headers, `res.write()` để gửi chunk dữ liệu và `res.end()` để hoàn tất kết nối HTTP.
3. Kế thừa: `http.Server` kế thừa từ `net.Server` và `EventEmitter`, kích hoạt các sự kiện `'request'`, `'connection'`, `'close'`.
💻 Code Ví Dụ Minh Họa & Output 
const http = require('node:http');

const server = http.createServer((req, res) => {
  const { method, url } = req;
  
  if (method === 'GET' && url === '/api/health') {
    res.writeHead(200, { 'Content-Type': 'application/json' });
    return res.end(JSON.stringify({ status: 'OK', uptime: process.uptime() }));
  }
  
  if (method === 'POST' && url === '/api/echo') {
    let body = '';
    req.on('data', chunk => { body += chunk; });
    req.on('end', () => {
      res.writeHead(200, { 'Content-Type': 'application/json' });
      res.end(JSON.stringify({ received: body }));
    });
    return;
  }

  res.writeHead(404, { 'Content-Type': 'text/plain' });
  res.end('Route Not Found');
});

server.listen(4000, () => console.log('HTTP Server listening on port 4000'));
💡 Điểm Cộng & Bẫy Phỏng Vấn (Gotchas / Senior Tips)
Điểm chú ý: Luôn gọi `res.end()` để đóng kết nối client. Nếu quên gọi `res.end()`, request từ trình duyệt/client sẽ bị treo vĩnh viễn (timeout).

What are streams in Node.js and what types are available?

🇻🇳 Streams trong Node.js là gì và có những loại Stream nào?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Stream là đối tượng cho phép đọc dữ liệu từ một nguồn hoặc ghi dữ liệu đến một đích theo từng mảnh nhỏ (chunks) một cách liên tục mà không cần phải tải toàn bộ file vào bộ nhớ RAM. Có 4 loại Stream cơ bản: Readable (đọc), Writable (ghi), Duplex (cả đọc và ghi), và Transform (biến đổi dữ liệu trên đường truyền).
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Bốn loại Stream:
- `Readable`: Ví dụ `fs.createReadStream`, `http.IncomingMessage` (req).
- `Writable`: Ví dụ `fs.createWriteStream`, `http.ServerResponse` (res).
- `Duplex`: Cả 2 chiều độc lập, ví dụ `net.Socket`.
- `Transform`: Duplex stream vừa nhận dữ liệu vừa biến đổi, ví dụ `zlib.createGzip()`.
2. Vấn đề Backpressure: Xảy ra khi nguồn đọc gửi dữ liệu nhanh hơn tốc độ mà đích ghi có thể xử lý. Nếu không kiểm soát, RAM sẽ phình to dẫn đến Crash OOM.
3. Giải pháp: Sử dụng `stream.pipeline()` thay cho `.pipe()` thủ công để tự động quản lý backpressure và xử lý lỗi/dọn dẹp tài nguyên triệt để.
💻 Code Ví Dụ Minh Họa & Output 
const fs = require('node:fs');
const zlib = require('node:zlib');
const { pipeline } = require('node:stream/promises');

async function compressLargeFile() {
  try {
    // Đọc file lớn -> Nén Gzip -> Ghi ra file mới
    // Bộ nhớ RAM duy trì ổn định dưới 30MB dù file gốc nặng 5GB!
    await pipeline(
      fs.createReadStream('huge_database_dump.sql'),
      zlib.createGzip(),
      fs.createWriteStream('huge_database_dump.sql.gz')
    );
    console.log('Nén file dung lượng lớn thành công bằng Stream Pipeline!');
  } catch (err) {
    console.error('Lỗi trong chuỗi Stream:', err);
  }
}

compressLargeFile();

Điểm cộng lớn khi phỏng vấn: Giải thích vì sao `pipeline()` tốt hơn `.pipe()`. Cú pháp `.pipe()` cũ không tự động hủy (destroy) các stream thượng nguồn khi có lỗi xảy ra ở downstream, dễ gây rò rỉ file descriptor.

How do you read and write files in Node.js?

🇻🇳 Cách đọc và ghi file trong Node.js hiệu quả nhất?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Tùy thuộc vào dung lượng file: Với file nhỏ (dưới 10MB), sử dụng fs/promises (readFile, writeFile) cho code đơn giản và tiện lợi. Với file lớn (từ vài chục MB đến hàng GB), bắt buộc dùng fs.createReadStream và fs.createWriteStream kết hợp stream.pipeline để stream dữ liệu.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Giới hạn V8 Buffer: V8 heap memory mặc định ~1.4GB trên 64-bit OS. Nếu dùng `fs.readFile` đọc file 2GB, Node.js sẽ ném lỗi `RangeError: File size is greater than possible Buffer: 0x7fffffff bytes`.
2. Line-by-line reading: Đọc từng dòng của file log hàng triệu dòng bằng module `readline` kết hợp ReadStream để memory tiêu tốn gần như bằng 0.
💻 Code Ví Dụ Minh Họa & Output 
const fs = require('node:fs');
const readline = require('node:readline');

async function readLogLineByLine(filePath) {
  const fileStream = fs.createReadStream(filePath);
  
  // Đọc từng dòng một, không tải hết file vào RAM
  const rl = readline.createInterface({
    input: fileStream,
    crlfDelay: Infinity
  });

  let errorCount = 0;
  for await (const line of rl) {
    if (line.includes('[ERROR]')) errorCount++;
  }

  console.log(`Tìm thấy tổng cộng ${errorCount} dòng lỗi.`);
}

How do you use the EventEmitter in Node.js?

🇻🇳 Cách sử dụng `EventEmitter` trong Node.js?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
EventEmitter nằm trong module events. Ta có thể kế thừa hoặc khởi tạo một instance của EventEmitter, đăng ký xử lý sự kiện bằng các phương thức .on(), .once(), và phát sự kiện bằng .emit(eventName, ...args).
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Các phương thức cốt lõi:
- `on(event, listener)`: Lắng nghe nhiều lần.
- `once(event, listener)`: Chỉ kích hoạt duy nhất một lần rồi tự hủy listener.

▾

Explain promises in Node.js.

🇻🇳 Giải thích về Promises trong Node.js?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Promise là một đối tượng đại diện cho kết quả cuối cùng (thành công hoặc thất bại) của một tác vụ bất đồng bộ. Một Promise có 3 trạng thái: Pending (đang chờ), Fulfilled (hoàn thành thành công với giá trị), và Rejected (thất bại với lý do/lỗi).
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Bất biến (Immutability): Khi một Promise đã chuyển sang Fulfilled hoặc Rejected, trạng thái của nó được đóng băng vĩnh viễn và không thể thay đổi.
2. Chaining: Cho phép nối chuỗi các tác vụ tuần tự qua `.then()`, mỗi `.then()` trả về một Promise mới.
3. Utility Methods hữu ích:
- `Promise.all([p1, p2])`: Chạy song song, thất bại ngay nếu 1 promise lỗi (Fail-fast).
- `Promise.allSettled()`: Chờ TẤT CẢ promises hoàn thành dù thành công hay lỗi.
- `Promise.race()`: Lấy kết quả của promise hoàn thành nhanh nhất.
💻 Code Ví Dụ Minh Họa & Output 
// Tạo một Promise
function checkServerStatus(url) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      const isOnline = true;
      if (isOnline) resolve({ url, status: 'Online', code: 200 });
      else reject(new Error('Server Offline'));
    }, 200);
  });
}

// Chạy song song nhiều promises

  checkServerStatus('https://api.domain1.com'),
  checkServerStatus('https://api.domain2.com')

    else console.log('Thất bại:', res.reason.message);
  });
});

▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
async/await là cú pháp 'đường cú pháp' (syntactic sugar) được xây dựng trên nền tảng của Promises và Generators. Từ khóa async biến một hàm thành một hàm luôn trả về một Promise, và từ khóa await tạm dừng việc thực thi bên trong hàm async cho đến khi Promise được giải quyết (resolve), mà không hề block luồng chính của Event Loop.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Dưới tầng V8: Khi gặp `await`, V8 lưu lại execution context của hàm async vào microtask queue và nhường quyền điều khiển CPU lại cho Event Loop để tiếp tục xử lý các sự kiện khác.
2. Xử lý lỗi: Dùng cấu trúc `try/catch` chuẩn của JavaScript, giúp bắt cả lỗi đồng bộ lẫn lỗi bất đồng bộ tại cùng một block code.
3. Chạy song song vs Tuần tự: Tránh việc lạm dụng `await` tuần tự các tác vụ độc lập. Hãy dùng `Promise.all([task1(), task2()])` để tối đa hóa hiệu năng I/O.

How does Node.js handle HTTP requests and responses?

🇻🇳 Node.js xử lý các HTTP Requests và Responses như thế nào?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Khi một client gửi HTTP Request, OS tạo một TCP socket kết nối với server. Parser HTTP nội bộ của Node.js (llhttp viết bằng C) sẽ phân tích gói tin stream. Đối tượng IncomingMessage (Readable Stream) và ServerResponse (Writable Stream) được khởi tạo và truyền vào callback của sự kiện 'request'.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Phân luồng dữ liệu dạng Chunk: Dữ liệu body được chia thành các Buffer chunks phát ra qua sự kiện `'data'`. Khi kết thúc body, sự kiện `'end'` được kích hoạt.
2. Keep-Alive: Mặc định HTTP 1.1 tái sử dụng kết nối TCP cho nhiều requests tiếp theo của cùng một client để giảm độ trễ handshake TCP.
3. Xử lý Headers: Headers được gửi đi ngay khi dòng đầu tiên của body được ghi hoặc khi gọi `res.writeHead()`. Sau khi headers đã gửi, nếu cố gắng gọi `res.setHeader()` sẽ gây ra lỗi kinh điển `ERR_HTTP_HEADERS_SENT`.
💻 Code Ví Dụ Minh Họa & Output 
const http = require('node:http');

  console.log(`Nhận request: ${req.method} ${req.url}`);
  
  // Kiểm tra header

  // Set headers trả về
  res.setHeader('X-Powered-By', 'Node.js Core');

  // Ghi body và hoàn tất
  res.end(JSON.stringify({
    message: 'Request đã được xử lý thành công',
    clientAgent: userAgent
  }));
}).listen(8080);

What is middleware in the context of Node.js?

▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Middleware là các hàm trung gian có quyền truy cập vào đối tượng Request (req), Response (res), và hàm next() trong chu trình request-response của ứng dụng. Middleware có thể thực thi mã, thay đổi req/res, kết thúc chu trình trả response, hoặc gọi next() để chuyển quyền cho middleware kế tiếp.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động

2. Các loại Middleware:
- Application-level middleware: `app.use(fn)`
- Router-level middleware: `router.use(fn)`
- Error-handling middleware: Nhận đủ 4 tham số `(err, req, res, next)`
- Built-in middleware: `express.json()`, `express.static()`
- Third-party middleware: `cors`, `helmet`, `morgan`.

How do you ensure security in HTTP headers with Node.js?

🇻🇳 Cách bảo vệ an toàn HTTP Headers trong ứng dụng Node.js?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Cách chuẩn mực và nhanh nhất là sử dụng thư viện helmet. Helmet tự động thiết lập hoặc loại bỏ các HTTP response headers quan trọng nhằm ngăn chặn các cuộc tấn công web phổ biến như XSS, Clickjacking, MIME sniffing, và ẩn thông tin công nghệ máy chủ.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
Các headers an ninh quan trọng mà Helmet cấu hình:
1. `Content-Security-Policy` (CSP): Giới hạn nguồn gốc các script, style, hình ảnh được phép tải.
2. `X-Frame-Options: SAMEORIGIN` / `DENY`: Chống tấn công Clickjacking (không cho iframe trang web trên domain lạ).
3. `X-Content-Type-Options: nosniff`: Ngăn chặn trình duyệt tự ý đoán sai MIME type.
4. `Strict-Transport-Security` (HSTS): Bắt buộc trình duyệt chỉ kết nối qua HTTPS.
5. Ẩn `X-Powered-By`: Xóa header tiết lộ bạn đang dùng Node.js/Express để hacker không thể khai thác lỗ hổng đã biết.
💻 Code Ví Dụ Minh Họa & Output

// Tùy chỉnh cụ thể Content Security Policy nếu cần

  helmet.contentSecurityPolicy({
    directives: {
      defaultSrc: ["'self'"],
      scriptSrc: ["'self'", "https://trustedscripts.com"],
    },
  })
);

app.get('/', (req, res) => res.send('Secure Node Server!'));

▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
process.nextTick() không phải là một phần kỹ thuật của Event Loop libuv. Thay vào đó, nó đưa callback vào một hàng đợi đặc biệt gọi là nextTickQueue. Hàng đợi này được Node.js vét sạch (xử lý ngay lập tức) ngay sau khi thao tác JavaScript hiện tại kết thúc, TRƯỚC KHI Event Loop tiếp tục bước sang pha kế tiếp.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Mức độ ưu tiên: `nextTickQueue` có độ ưu tiên cao hơn cả `Promise.then` (microtask queue) và cao hơn rất nhiều so với `setImmediate` hay `setTimeout`.
2. Nguy cơ làm đói I/O (I/O Starvation): Nếu bạn gọi đệ quy `process.nextTick()`, Event Loop sẽ bị 'bỏ đói' hoàn toàn vì không bao giờ đến được pha Poll để nhận I/O mới hay xử lý network!
3. Trường hợp sử dụng thực tế: Cho phép một hàm phát ra sự kiện hoặc chạy callback bất đồng bộ NGAY SAU KHI hàm gọi nó đã hoàn thành việc gán biến, nhưng trước khi bất kỳ I/O nào khác diễn ra.

  const emitter = new EventEmitter();

  process.nextTick(() => {
    emitter.emit('ready', { status: 'Database connected' });
  });
  
  return emitter;
}

const pool = mysql.createPool({
  host: process.env.DB_HOST || 'localhost',
  user: process.env.DB_USER || 'root',
  password: process.env.DB_PASSWORD || 'secret',
  database: 'ecommerce_db',
  waitForConnections: true,
  connectionLimit: 15, // Tối đa 15 kết nối đồng thời
  queueLimit: 0

  // ✅ An toàn chống SQL Injection với Prepared Statements

What is clustering in Node.js and how does it work?

🇻🇳 Clustering trong Node.js là gì và nó hoạt động như thế nào?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Clustering là cơ chế cho phép tận dụng tối đa tất cả các nhân (cores) của CPU trên máy chủ bằng cách khởi tạo một nhóm các tiến trình Node.js con (workers) cùng chia sẻ một cổng mạng duy nhất. Module cluster sử dụng tiến trình cha (Primary/Master) để phân phối các kết nối đến các tiến trình con bằng thuật toán Round-Robin.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Cơ chế chia sẻ Port: Master process lắng nghe trên cổng (ví dụ 3000), khi có kết nối TCP mới, Master chuyển giao trực tiếp socket file descriptor qua kênh IPC (Inter-Process Communication) cho một worker rảnh rỗi.
2. Độc lập bộ nhớ: Mỗi worker là một process độc lập với V8 instance và memory heap riêng biệt (~30MB-50MB RAM mỗi worker). Nếu một worker bị crash do lỗi, Master có thể fork ngay worker mới thay thế (Zero Downtime).
3. Hạn chế: Vì không chia sẻ bộ nhớ, trạng thái phiên (sessions) hoặc cache trong RAM biến cục bộ không thể dùng chung giữa các workers -> Cần Redis làm external store.
💻 Code Ví Dụ Minh Họa & Output 
const cluster = require('node:cluster');
const http = require('node:http');
const os = require('node:os');

if (cluster.isPrimary) {
  const numCPUs = os.cpus().length;
  console.log(`Primary Master ${process.pid} đang khởi chạy trên ${numCPUs} CPU cores...`);

  // Fork các workers bằng số nhân CPU
  for (let i = 0; i < numCPUs; i++) {
    cluster.fork();
  }

  // Tự động hồi sinh worker nếu bị chết (Auto-recovery)
  cluster.on('exit', (worker, code, signal) => {
    console.log(`Worker ${worker.process.pid} bị dừng (${signal || code}). Đang tạo worker mới...`);
    cluster.fork();
  });
} else {
  // Các Workers cùng chia sẻ port 8000
  http.createServer((req, res) => {
    res.writeHead(200);
    res.end(`Phản hồi từ Worker PID: ${process.pid}\n`);
  }).listen(8000);
  
  console.log(`Worker ${process.pid} đã sẵn sàng.`);
}

How can you prevent memory leaks in a Node.js application?

🇻🇳 Cách phát hiện và ngăn ngừa rò rỉ bộ nhớ (Memory Leaks) trong ứng dụng Node.js?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Rò rỉ bộ nhớ trong Node.js xảy ra khi các đối tượng không còn sử dụng nhưng vẫn bị tham chiếu bởi một chuỗi tham chiếu gốc (GC Root), khiến V8 Garbage Collector không thể thu hồi. Các nguyên nhân phổ biến nhất: Biến toàn cục vô tình tạo ra, Closures giữ lại scope lớn, EventListeners không được gỡ bỏ, và lưu trữ Cache trong bộ nhớ trong (in-memory) không có giới hạn.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Các nguyên nhân hàng đầu:
- `EventEmitter` leaks: Gắn listener vào singleton event mà quên `.removeListener()`.
- In-memory Object Cache: Dùng một object `const cache = {}` lưu trữ mọi thứ mãi mãi mà không dùng thuật toán LRU (Least Recently Used) hay giới hạn TTL.
- Timers (`setInterval`): Quên gọi `clearInterval`.
2. Cách phát hiện:
- Chụp Heap Snapshots bằng `--inspect` qua Chrome DevTools hoặc `v8.getHeapSnapshot()`.
- So sánh 2 file snapshot (Comparison View) để tìm đối tượng nào tăng đột biến.

How does Node.js handle concurrency?

▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Node.js xử lý đồng thời dựa trên kiến trúc Non-blocking I/O và Reactor Pattern. Bản thân code JavaScript chạy trên một luồng duy nhất (Single Thread), nhưng các thao tác I/O tốn thời gian (Network, Disk, Database) được ủy thác cho hạt nhân hệ điều hành (thông qua epoll trên Linux, kqueue trên macOS, IOCP trên Windows) hoặc libuv thread pool. 🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Phân biệt Concurrency vs Parallelism:
- Concurrency (Đồng thời): Xử lý nhiều việc trong cùng một khoảng thời gian bằng cách chuyển đổi giữa chúng (giao việc cho OS và tiếp tục nhận request mới). Đây là cách Node.js hoạt động.
- Parallelism (Song song): Thực sự chạy nhiều tác vụ cùng một thời điểm trên nhiều CPU cores vật lý (Node.js dùng Worker Threads hoặc Cluster để đạt được điều này).
2. Lợi thế: Không cần khóa đồng bộ (mutexes, locks, semaphores) nên hoàn toàn tránh được lỗi Deadlock phức tạp của các ngôn ngữ đa luồng truyền thống.

What are WebSockets and how do they work with Node.js?

🇻🇳 WebSockets là gì và chúng hoạt động với Node.js như thế nào?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
WebSockets là giao thức mạng cung cấp kênh giao tiếp song công toàn phần (Full-Duplex), hai chiều, liên tục trên một kết nối TCP duy nhất giữa client và server. Không giống như HTTP (phải gửi request mới có response), WebSocket cho phép server chủ động đẩy dữ liệu (push) xuống client ngay lập tức khi có sự kiện với độ trễ cực thấp.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Handshake: Kết nối bắt đầu bằng một HTTP GET Request bình thường với header `Upgrade: websocket` và `Connection: Upgrade`. Server phản hồi `101 Switching Protocols` để chuyển sang giao thức WebSocket nhị phân.
2. Trọng lượng nhẹ: Sau khi kết nối được nâng cấp, các frame dữ liệu chỉ tốn 2 đến 10 bytes overhead (so với hàng trăm bytes headers của mỗi HTTP request).
3. Thư viện phổ biến: `ws` (siêu nhanh, nhẹ, chuẩn RFC 6455) và `Socket.IO` (có fallback polling, tự động reconnect, rooms).
💻 Code Ví Dụ Minh Họa & Output 
const http = require('node:http');
const { WebSocketServer } = require('ws');

const server = http.createServer();
const wss = new WebSocketServer({ server });

wss.on('connection', (ws, req) => {
  const clientIp = req.socket.remoteAddress;
  console.log(`Client mới kết nối từ: ${clientIp}`);

  // Gửi tin nhắn chào mừng
  ws.send(JSON.stringify({ type: 'WELCOME', message: 'Kết nối WebSocket thành công!' }));

  // Lắng nghe tin nhắn từ client
  ws.on('message', (data) => {
    console.log('Nhận dữ liệu:', data.toString());
    
    // Broadcast cho TẤT CẢ các client khác đang kết nối
    wss.clients.forEach(client => {
      if (client !== ws && client.readyState === ws.OPEN) {
        client.send(data);
      }
    });
  });
});

server.listen(8080, () => console.log('WebSocket Server running on ws://localhost:8080'));

How do you set up a WebSocket server in Node.js?

▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Thư viện ws là giải pháp chuẩn công nghiệp nhanh và nhẹ nhất cho Node.js WebSocket. Ta thiết lập bằng cách gắn WebSocketServer vào HTTP server hiện có hoặc mở một cổng độc lập, cài đặt Ping/Pong định kỳ để dọn dẹp các kết nối ngắt đột ngột và xử lý xác thực token trong quá trình handshake.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Xác thực an toàn: Kiểm tra JWT token ngay trong sự kiện `'upgrade'` của HTTP server trước khi chấp nhận nâng cấp kết nối. Nếu token sai, từ chối ngay lập tức với mã `401 Unauthorized`.
2. Heartbeat (Giữ kết nối): Sử dụng cờ `isAlive = true` khi nhận sự kiện `'pong'`. Định kỳ mỗi 30s gọi `ws.ping()`. Nếu socket nào không trả lời pong, gọi `ws.terminate()` để giải phóng socket descriptor.
💻 Code Ví Dụ Minh Họa & Output 
const { WebSocketServer } = require('ws');

const wss = new WebSocketServer({ port: 8081 });

// Cài đặt cơ chế Ping/Pong phát hiện zombie socket
function heartbeat() {
  this.isAlive = true;
}

wss.on('connection', (ws) => {
  ws.isAlive = true;
  ws.on('pong', heartbeat);
});

const interval = setInterval(() => {
  wss.clients.forEach((ws) => {
    if (ws.isAlive === false) return ws.terminate(); // Hủy kết nối chết
    ws.isAlive = false;
    ws.ping(); // Gửi ping đến client
  });
}, 30000);

wss.on('close', () => clearInterval(interval));

What are semantic versioning (semver) and its importance in Node.js development?

🇻🇳 Semantic Versioning (SemVer) là gì và tầm quan trọng của nó trong Node.js?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Semantic Versioning (SemVer) là quy ước đặt tên phiên bản phần mềm theo chuẩn format MAJOR.MINOR.PATCH (Ví dụ: 2.4.1). SemVer giúp các nhà phát triển và công cụ quản lý gói npm hiểu được mức độ thay đổi của mã nguồn và tự động nâng cấp an toàn.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
Ý nghĩa của từng số:
1. `MAJOR` (ví dụ 1.0.0 -> 2.0.0): Tăng khi có các thay đổi làm gãy tính tương thích ngược (Breaking Changes / Incompatible API changes).
2. `MINOR` (ví dụ 2.4.0 -> 2.5.0): Tăng khi thêm tính năng mới nhưng vẫn hoàn toàn tương thích ngược (Backwards-compatible functionality).
3. `PATCH` (ví dụ 2.5.1 -> 2.5.2): Tăng khi sửa lỗi bugs và hoàn toàn tương thích ngược (Backwards-compatible bug fixes).
* Ký hiệu trong package.json:
- `^1.2.3` (Caret): Cho phép cập nhật minor và patch (< 2.0.0).
- `~1.2.3` (Tilde): Chỉ cho phép cập nhật patch (< 1.3.0).

What is the difference between exports and module.exports in Node.js?

🇻🇳 Sự khác biệt giữa `exports` và `module.exports` trong CommonJS?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Trong CommonJS, module.exports là đối tượng THỰC TẾ được hàm require() trả về. Biến exports ban đầu chỉ đơn thuần là một biến tham chiếu (shortcut / alias) trỏ đến cùng vùng nhớ của module.exports. Nếu bạn gán lại exports = myFunction, bạn đã bẻ gãy mối liên kết tham chiếu đó và hàm sẽ không được xuất ra ngoài!
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Cơ chế nội bộ của Node.js:
Trước khi chạy file, Node.js bọc code trong Module Wrapper:
`(function (exports, require, module, __filename, __dirname) { ... })`
Trong đó `exports = module.exports = {};`
2. Đúng: `exports.foo = 'bar'` (thêm thuộc tính vào đối tượng chung).
3. Đúng: `module.exports = class User {}` (xuất ra class hoặc function duy nhất).
4. Sai: `exports = class User {}` (không có tác dụng, require vẫn nhận về `{}`).

// === logger.js ===
// ✅ CÁCH 2: Xuất trực tiếp 1 hàm hoặc class bằng module.exports

  console.log(`[LOG]: ${msg}`);
};

How do Node.js streams enhance performance?

▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Streams nâng cao hiệu năng thông qua 2 yếu tố cốt tử: (1) Hiệu quả Không gian (Spatial Efficiency): Dữ liệu được xử lý theo từng khối nhỏ (chunks mặc định 16KB-64KB), giúp bộ nhớ RAM không bao giờ bị phình to theo kích thước file, và (2) Hiệu quả Thời gian (Temporal Efficiency): Bắt đầu xử lý và truyền dữ liệu cho client ngay lập tức khi chunk đầu tiên sẵn sàng mà không cần đợi tải xong toàn bộ dữ liệu.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Tiết kiệm thời gian: Client có thể xem video hoặc giải nén dữ liệu ngay khi byte đầu tiên được stream tới.
2. Backpressure Control: Khi Stream Writable bị đầy bộ đệm (highWaterMark), nó gửi tín hiệu bảo Stream Readable tạm dừng đọc (`drain` event). Cơ chế này ngăn chặn hiện tượng tràn bộ nhớ khi máy khách mạng chậm tải từ máy chủ mạng siêu tốc.
3. Chống Crash OOM: Cho phép ứng dụng xử lý file dữ liệu 50GB trên một máy chủ RAM chỉ có 512MB.

🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Timeout: Không bao giờ gửi request mà không có timeout! Mặc định nhiều thư viện không có timeout, nếu bên thứ ba bị lag, hàng ngàn requests của bạn sẽ bị nghẽn dẫn đến cạn kiệt tài nguyên server.
2. Circuit Breaker: Thư viện `opossum` giúp theo dõi tỉ lệ lỗi. Nếu bên thứ ba fail quá 50%, circuit mở (Open), các request sau sẽ trả lỗi ngay lập tức hoặc dùng fallback cache mà không cần tốn thời gian gọi sang bên thứ ba nữa.

// Sử dụng Native Fetch với AbortController để đặt Timeout chặt chẽ
async function callPartnerApiWithTimeout(endpoint, timeoutMs = 3000) {
  const controller = new AbortController();
  const timeoutId = setTimeout(() => controller.abort(), timeoutMs);

  try {
    const response = await fetch(endpoint, {
      signal: controller.signal,
      headers: {
        'Authorization': `Bearer ${process.env.PARTNER_API_KEY}`,
        'Content-Type': 'application/json'
      }
    });

    if (!response.ok) {
      throw new Error(`Partner API HTTP Error: ${response.status}`);
    }

    return await response.json();
  } catch (error) {
    if (error.name === 'AbortError') {
      console.error(`Request bị hủy do quá thời gian chờ ${timeoutMs}ms`);
    }
    throw error;
  } finally {
    clearTimeout(timeoutId); // Dọn dẹp timer
  }
}

How do you implement RabbitMQ with Node.js?

🇻🇳 Cách triển khai RabbitMQ trong Node.js sử dụng thư viện `amqplib`?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Sử dụng thư viện amqplib (hỗ trợ Promise/async-await). Quy trình triển khai bao gồm: (1) Kết nối đến RabbitMQ server (amqp.connect), (2) Tạo kênh giao tiếp (createChannel), (3) Khai báo hàng đợi (assertQueue với cờ durable: true), (4) Gửi tin nhắn bằng sendToQueue, và (5) Phía consumer sử dụng channel.consume() và BẮT BUỘC gọi channel.ack() để xác nhận hoàn thành.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Cơ chế Acknowledgment (`ack` vs `nack`): Nếu worker bị crash giữa chừng trước khi gửi `ack`, RabbitMQ sẽ giữ lại tin nhắn và tự động gửi lại cho worker khác (đảm bảo không mất dữ liệu).
2. Prefetch Count (`channel.prefetch(1)`): Cực kỳ quan trọng! Giới hạn mỗi worker chỉ nhận đúng 1 tin nhắn tại một thời điểm, làm xong mới nhận tiếp, giúp cân bằng tải đều giữa các workers (Fair Dispatch) thay vì chia đều mù quáng (Round-robin).
💻 Code Ví Dụ Minh Họa & Output 
const amqp = require('amqplib');

async function startRabbitMQWorker() {
  const conn = await amqp.connect('amqp://localhost');
  const channel = await conn.createChannel();
  const queue = 'order_processing';

  await channel.assertQueue(queue, { durable: true });
  
  // Chỉ nhận 1 job tại 1 thời điểm
  channel.prefetch(1);

  console.log('Worker đang chờ nhận đơn hàng từ RabbitMQ...');

  channel.consume(queue, async (msg) => {
    if (msg !== null) {
      const order = JSON.parse(msg.content.toString());
      console.log('Đang xử lý đơn hàng:', order.id);

      try {
        // Thực hiện logic xử lý...
        channel.ack(msg); // ✅ Báo cáo RabbitMQ: Đã hoàn tất, có thể xóa job!
      } catch (err) {
        // Gặp lỗi: requeue lại hoặc gửi vào Dead Letter Exchange
        channel.nack(msg, false, false);
      }
    }
  });
}

startRabbitMQWorker();

on:
  push:
    branches: [ main ]
  pull_request:
    branches: [ main ]

jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:

async function streamAiResponse(prompt, res) {
  const stream = await openai.chat.completions.create({
    model: 'gpt-4o',
    messages: [{ role: 'user', content: prompt }],
    stream: true // Kích hoạt Server-Sent Events Stream
  });

  res.setHeader('Content-Type', 'text/event-stream');
  for await (const chunk of stream) {
    const text = chunk.choices[0]?.delta?.content || '';
    res.write(`data: ${text}\n\n`); // Stream từng từ về cho client
  }
  res.end();
}

Câu 100 Senior APIs and Node.js

What are best practices for designing RESTful APIs in Node.js?

🇻🇳 Tổng hợp các Best Practices toàn diện nhất khi thiết kế RESTful API trong Node.js?
▾
🎯 Tóm Tắt Trọng Tâm Phỏng Vấn (30s Pitch)
Một RESTful API đẳng cấp doanh nghiệp trong Node.js cần hội tụ đầy đủ: (1) Tuân thủ chuẩn đặt tên URI dạng danh từ số nhiều phân cấp rõ ràng, (2) Quản lý phiên bản chặt chẽ (/api/v1/), (3) Áp dụng phân trang (Cursor-based Pagination cho dữ liệu lớn), (4) Sử dụng HTTP Status Codes và cấu trúc phản hồi lỗi đồng nhất, (5) Bảo mật nhiều lớp (Helmet, Rate-limit, CORS, Input validation), (6) Nén dữ liệu gzip và hỗ trợ ETag caching, và (7) Tài liệu hóa tự động bằng OpenAPI / Swagger.
🔍 Giải Thích Chuyên Sâu & Cơ Chế Hoạt Động
1. Cấu trúc phản hồi lỗi đồng nhất (Uniform Error Response):
Mọi lỗi trả về cho client nên tuân theo định dạng chuẩn (ví dụ RFC 7807 Problem Details):
`{ success: false, error: { code: 'INVALID_INPUT', message: '...', details: [...] } }`
2. Phân trang: Thay vì dùng `OFFSET` chậm chạp trên hàng triệu dòng, hãy dùng Keyset / Cursor Pagination (`?limit=20&after_cursor=...`).
3. Idempotency: Hỗ trợ header `Idempotency-Key` cho các endpoint thanh toán và tạo đơn hàng.
