Câu 3: Khi nào nên dùng tuple thay vì list?
✅ 4 lý do chọn tuple thay vì list:
  1. Bảo vệ dữ liệu không bị sửa nhầm (Write-protection): Khi dữ liệu là hằng số hoặc bản ghi cố định (ví dụ tọa độ (21.0285, 105.8542)), dùng tuple đảm bảo không hàm nào vô tình .append() hay sửa mất dữ liệu.
  2. Làm Key cho dict hoặc phần tử của set (Hashable): list không thể làm key trong dict (sẽ báo lỗi TypeError: unhashable type: 'list'), còn tuple (nếu chứa các phần tử bất biến) thì làm key được: cache[(user_id, page)] = data.
  3. Tiết kiệm RAM và tạo nhanh hơn list: Vì kích thước cố định, Python cấp phát vừa khít bộ nhớ cho tuple (không cần over-allocation dự phòng như list).
Câu 4: Sự khác nhau giữa == và is trong Python?
  • == (Equality — So sánh GIÁ TRỊ): Kiểm tra xem 2 biến có giá trị bên trong bằng nhau hay không (gọi hàm __eq__()).
  • is (Identity — So sánh ĐỊA CHỈ Ô NHỚ): Kiểm tra xem 2 biến có trỏ tới cùng 1 object duy nhất trong RAM hay không (tương đương id(a) == id(b)).

print(a is b)  # False (Hai list nằm ở 2 ô nhớ khác nhau trong RAM!)

Câu 5: None, False, 0, "" (empty string) và [] (empty list) khác nhau như thế nào?
  • Điểm giống nhau: Cả 5 giá trị này đều là Falsy (khi đưa vào bool(x) hoặc if x: đều trả về False).
  • Điểm khác nhau: Chúng có kiểu dữ liệu và ý nghĩa hoàn toàn khác nhau:
    • None (kiểu NoneType): Biểu thị sự vắng mặt của dữ liệu / chưa có giá trị (giống NULL trong SQL).
    • False (kiểu bool): Giá trị logic Sai.
    • 0 (kiểu int): Con số không (ví dụ: price = 0 cho đơn hàng miễn phí — đây là dữ liệu hợp lệ, KHÔNG phải là thiếu dữ liệu!).
    • "" (kiểu str): Chuỗi rỗng độ dài 0.
    • [] (kiểu list): Danh sách rỗng chưa có phần tử.
💥 Bẫy Thực Tế Khi Đi Làm: Giả sử khách hàng nhập discount = 0 (giảm giá 0 đồng).
• Nếu bạn viết if not discount: ➡️ Khi discount = 0, Python coi 0 là Falsy và báo lỗi "Bạn chưa nhập discount!" (SAI!).
• Cách viết đúng: Phải viết if discount is None: để chỉ bắt trường hợp chưa truyền dữ liệu!

Câu 7: Sự khác nhau giữa local, global, nonlocal scope? Quy tắc LEGB?
Khi bạn gọi một biến trong Python, nó tìm kiếm theo quy tắc LEGB từ trong ra ngoài:
  1. L — Local: Biến khai báo bên trong hàm hiện tại.
  2. E — Enclosing (Nonlocal): Biến nằm trong hàm cha bao ngoài (khi có hàm lồng trong hàm / Closure). Muốn sửa biến của hàm cha phải dùng từ khóa nonlocal.
  3. G — Global: Biến khai báo ở cấp độ ngoài cùng của file module. Muốn gán lại biến global từ trong hàm phải dùng từ khóa global.
  4. B — Built-in: Các hàm/từ khóa có sẵn của Python như len, print, range.
x = "Global"

def outer():
    x = "Enclosing"
    def inner():
        nonlocal x  # Sửa biến x của hàm outer()! (Nếu dùng 'global x' sẽ sửa x ở ngoài cùng)
        x = "Modified Enclosing"
    inner()
    print(x)  # In ra: "Modified Enclosing"

            raise PermissionError("Chỉ Admin mới được thực hiện!")
        return func(user, *args, **kwargs)
    return wrapper

Câu 11: Kế thừa, Đa hình và Đóng gói trong Python được thể hiện như thế nào?
  • 1. Kế thừa (Inheritance): Lớp con kế thừa thuộc tính/phương thức từ lớp cha qua class Child(Parent): và gọi lớp cha bằng super().__init__(). Python hỗ trợ đa kế thừa (giải quyết thứ tự gọi hàm qua thuật toán MRO - Method Resolution Order: Child.mro()).
  • 2. Đa hình (Polymorphism): Thể hiện qua Method Overriding (lớp con định nghĩa lại hàm cùng tên của lớp cha) và Duck Typing (không cần cùng lớp cha, miễn có cùng hàm .pay() như MomoPayment.pay() và StripePayment.pay() là gọi chung được).
  • 3. Đóng gói (Encapsulation): Python dùng quy ước đặt tên kết hợp @property:
    • name (Public): Truy cập tự do.
    • _balance (Protected — 1 gạch dưới): Quy ước ngầm بين các dev "Chỉ dùng nội bộ trong class và class con, đừng gọi từ bên ngoài".
    • __pin (Private — 2 gạch dưới): Python thực hiện Name Mangling (đổi tên ngầm thành _BankAccount__pin) để tránh bị truy cập trực tiếp hoặc bị class con ghi đè nhầm.

Câu 13: Shallow Copy và Deep Copy khác nhau như thế nào?
Sự khác biệt chỉ xuất hiện khi bạn copy một Nested Object (Object lồng nhau, ví dụ list chứa list con [[1, 2], [3, 4]]):

Câu 14: Iterator và Iterable khác nhau như thế nào? Vòng for hoạt động ra sao?
  • Iterable (Khả duyệt): Bất kỳ object nào có thể lặp qua bằng vòng for (như list, tuple, str, dict). Nó cài đặt hàm __iter__() trả về một Iterator, nhưng bản thân nó không lưu vị trí đang duyệt tới đâu (có thể duyệt đi duyệt lại nhiều lần).
  • Iterator (Bộ lặp): Là object giữ trạng thái vị trí hiện tại, cài đặt cả __iter__() lẫn __next__(). Mỗi lần gọi next(it) nó trả về phần tử tiếp theo; khi hết phần tử nó ném ra ngoại lệ StopIteration (chỉ duyệt được 1 lần là cạn!).
  • Cách vòng lặp for x in my_list: hoạt động ngầm: Python gọi it = iter(my_list), sau đó lặp vô tận gọi x = next(it) cho đến khi bắt được StopIteration thì dừng vòng lặp!
Câu 15: Generator là gì? Ưu điểm của yield so với return?
  • Generator: Là cách đơn giản nhất để tạo một Iterator bằng cách viết một hàm có từ khóa yield (hoặc dùng biểu thức (x*2 for x in range(1000000))).
  • return vs yield:
    • return: Tính toán xong toàn bộ kết quả, trả về 1 lần và xóa sổ hàm khỏi bộ nhớ.
    • yield (Lazy Evaluation): Trả về từng giá trị một khi được yêu cầu, tạm dừng (pause) hàm và giữ nguyên toàn bộ biến local tại dòng đó. Lần gọi next() tiếp theo, hàm chạy tiếp ngay từ dòng sau yield!
  • Ưu điểm lớn nhất: Tiết kiệm bộ nhớ RAM cực khủng ($O(1)$ RAM) — xử lý 10 triệu bản ghi hoặc đọc file log 20 GB mà chỉ tốn vài KB RAM!
Câu 16: List Comprehension có ưu/nhược điểm gì?
  • Ưu điểm:
    1. Ngắn gọn, dễ đọc với các phép biến đổi/lọc đơn giản: evens = [x for x in nums if x % 2 == 0].
    2. Nhanh hơn vòng for thường + .append() khoảng 15–30% vì được tối ưu ở mức C-bytecode (LIST_APPEND) thay vì phải tra cứu method .append ở mỗi vòng lặp.
  • Nhược điểm:
    1. Khởi tạo toàn bộ danh sách trong RAM cùng lúc ➡️ Nếu dữ liệu hàng triệu phần tử sẽ gây tràn RAM (khi đó nên đổi ngoặc vuông [...] thành ngoặc tròn (...) Generator Expression!).
    2. Nếu lồng 2–3 vòng for hoặc if/else phức tạp sẽ cực kỳ rối mắt, khó đặt breakpoint debug.

Câu 18: Vì sao không nên dùng except Exception: hoặc except: trống quá rộng?
  • 1. Che giấu bug ngầm (Silent Failures): Nếu bạn gõ sai tên biến (NameError) hoặc sai kiểu dữ liệu (TypeError) bên trong try, một cái except: pass sẽ nuốt chửng lỗi đó khiến chương trình chạy sai kết quả mà không báo dòng nào bị lỗi!
  • 2. Bare except: bắt luôn cả lệnh tắt chương trình! Khi bạn bấm Ctrl+C (KeyboardInterrupt) hoặc gọi sys.exit() (SystemExit), bare except: sẽ chặn không cho chương trình dừng lại!
  • ✅ Nguyên tắc vàng: Luôn bắt đúng Exception cụ thể (ví dụ except (ValueError, KeyError) as e:) và ghi log đầy đủ (logger.exception(e)).
Câu 19: Context Manager là gì? Tại sao nên dùng with khi làm việc với file?
  • Context Manager: Là một object quản lý vòng đời tài nguyên (File, Database Connection, Socket, Thread Lock) thông qua 2 hàm magic: __enter__(self) (cấp phát tài nguyên khi vào khối with) và __exit__(self, exc_type, exc_val, exc_tb) (tự động dọn dẹp/đóng tài nguyên khi thoát khỏi khối with).
  • Tại sao phải dùng with open("data.txt") as f:? Vì dù code bên trong khối with chạy thành công, có lệnh return sớm, hay bị văng Exception giữa chừng, Python vẫn đảm bảo 100% gọi __exit__() để đóng file (f.close()) ngay lập tức, tránh lỗi rò rỉ tài nguyên hệ điều hành (Too many open files)!
Câu 20 & 21: Module vs Package khác nhau thế nào? virtualenv / venv dùng để làm gì?
  • Câu 20 (Module vs Package):
    • Module: Là một file .py đơn lẻ (ví dụ: utils.py) chứa hàm, class, biến.
    • Package: Là một thư mục (directory) gom nhiều module lại với nhau và có chứa file __init__.py (ví dụ: orders/__init__.py, orders/models.py, orders/views.py).
  • Câu 21 (venv / virtualenv): Tạo một môi trường Python cô lập riêng cho từng project. Nhờ đó, Dự án A có thể chạy Django 3.2 còn Dự án B chạy Django 5.0 trên cùng một máy tính mà không bị đè thư viện lên nhau. 1.5 Concurrency & Performance (Câu 22 – Câu 25)

Câu 22 & 23: GIL là gì? Phân biệt threading, multiprocessing và asyncio?
1. GIL (Global Interpreter Lock): Là một khóa (mutex) bên trong CPython chỉ cho phép tối đa 1 luồng (thread) thực thi Python bytecode tại một thời điểm trong cùng 1 process (để bảo vệ bộ đếm tham chiếu bộ nhớ Reference Counting không bị Race Condition).
2. Hệ quả thực tế:
  • Với tác vụ CPU-Bound (tính toán nặng, xử lý ảnh, vòng lặp lớn): Dùng nhiều threading KHÔNG làm chạy nhanh hơn vì các thread phải xếp hàng tranh nhau 1 cái GIL!
  • Với tác vụ I/O-Bound (gọi DB, gọi API, đọc file): Khi thread đang ngồi chờ mạng/DB phản hồi, Python tự động nhả GIL ra cho thread khác chạy!
Mô hình Cơ chế hoạt động Bài toán phù hợp nhất
threading Nhiều OS threads chạy trong 1 process, chia sẻ RAM, bị giới hạn bởi GIL khi chạy CPU. I/O-Bound đồng bộ (Sync I/O): Gọi 20 API bằng thư viện requests cũ hoặc đọc/ghi file đồng thời.
asyncio 1 Thread duy nhất dùng Event Loop + async/await (Cooperative multitasking). Siêu nhẹ RAM! I/O-Bound tải cực cao (High Concurrency): Web server FastAPI/ASGI xử lý 5,000 kết nối mạng/DB cùng lúc.
multiprocessing Tạo ra nhiều OS Process riêng biệt, mỗi process có một Python Interpreter và một GIL riêng (chạy tận dụng hết 100% đa nhân CPU). CPU-Bound: Xử lý ảnh/video, tính toán ma trận, nén file, Machine Learning.
Câu 24 & 25: Làm sao tối ưu hiệu năng Python? Big-O notation trong list vs dict/set lookup?
  • Câu 25 (Big-O Notation): Đo lường tốc độ tăng thời gian chạy (Time Complexity) hoặc bộ nhớ (Space Complexity) khi kích thước dữ liệu $N$ tăng lên:
    • x in my_list ➡️ $O(N)$ (Tuyến tính): Nếu list có 1,000,000 phần tử, Python phải duyệt qua từng phần tử từ đầu đến cuối (tối đa 1,000,000 phép so sánh!).
    • x in my_set hoặc x in my_dict ➡️ $O(1)$ (Hằng số): Python băm hash(x) để nhảy thẳng tới ô nhớ trong chỉ 1 bước duy nhất dù có 10 triệu phần tử!
    • Binary Search trên danh sách đã sắp xếp (`bisect`) ➡️ $O(\log N)$.
  • Câu 24 (Các bước tối ưu code Python thực tế):
    1. Đo đạc trước (Don't guess, Profile!): Dùng cProfile, time.perf_counter() hoặc APM để tìm đúng hàm gây nghẽn (tránh Premature Optimization).
    2. Chọn đúng Data Structure & Thuật toán: Đổi list lookup $O(N)$ sang set/dict $O(1)$; dùng collections.deque cho hàng đợi FIFO ($O(1)$ popleft() thay vì list.pop(0) tốn $O(N)$).
    3. Tối ưu Database & I/O: Khử N+1 query (select_related / prefetch_related), dùng Bulk Insert/Update (bulk_create), đánh Index DB.
    4. Tiết kiệm RAM & Caching: Dùng Generator (yield) cho dữ liệu lớn, dùng @functools.lru_cache hoặc Redis cho kết quả tính toán lặp lại.

2.3 View, Template, Form & CSRF (Câu 38 – Câu 42)

Câu 38 – 42: FBV vs CBV? request/response? Template Inheritance? Form vs ModelForm? Cơ chế CSRF?
  • Câu 38 (FBV vs CBV):
    • Function-Based View (FBV): Viết bằng hàm def my_view(request):, phân nhánh bằng if request.method == 'POST':. Ưu điểm: Tường minh, dễ đọc luồng xử lý phức tạp/đặc thù.
    • Class-Based View (CBV): Viết bằng class kế thừa View, ListView, CreateView. Tách phương thức theo tên hàm get(self, request), post(self, request). Ưu điểm: Tái sử dụng code cực nhanh cho CRUD chuẩn qua kế thừa và Mixin (như LoginRequiredMixin).
  • Câu 39 (request & response): request chứa request.GET (query params ?page=2), request.POST (form body), request.FILES (file upload), request.user (user đang đăng nhập), request.session, request.headers. response trả về HttpResponse, JsonResponse({"status": "ok"}), hoặc redirect().
  • Câu 40 (Template Inheritance): Tạo khung giao diện chung ở base.html với các lỗ trống {% block content %}{% endblock %}. Các trang con kế thừa bằng {% extends "base.html" %} để không phải lặp lại Header/Footer. Dùng {% include "navbar.html" %} để nhúng component nhỏ.
  • Câu 41 (Form vs ModelForm): forms.Form khai báo thủ công từng trường (dùng cho form không gắn trực tiếp với 1 bảng như Form Liên hệ, Form Đăng nhập, Form Tìm kiếm). forms.ModelForm tự động sinh các trường từ Model và có sẵn hàm form.save() để lưu thẳng vào Database! Dữ liệu hợp lệ sau khi gọi form.is_valid() nằm trong form.cleaned_data.
  • Câu 42 (CSRF Protection trong Django): Khi render trang HTML, Django cấp một csrf_token ngẫu nhiên (trong cookie và thẻ ẩn {% csrf_token %} trong form). Khi người dùng gửi POST/PUT/DELETE, CsrfViewMiddleware so sánh token trong form/header X-CSRFToken với token của phiên. Nếu trang web độc hại bên thứ 3 giả mạo gửi form POST sang, nó không đọc được csrf_token nên bị chặn ngay với lỗi 403 Forbidden!

2.4 Admin, Auth, Middleware & Session (Câu 43 – Câu 46)

Câu 43 – 46: Tùy biến Django Admin? Authentication vs Authorization? Middleware? Session vs Cookie?
  • Câu 43 (Tùy biến Django Admin): Trong ModelAdmin, ta tùy biến: list_display (các cột hiển thị trên bảng), search_fields (ô tìm kiếm), list_filter (bộ lọc bên phải), readonly_fields (trường chỉ đọc), prepopulated_fields = {"slug": ("title",)}, và inlines = [CommentInline] (chỉnh sửa bảng con ngay trong trang bảng cha).
  • Câu 44 (Authentication vs Authorization):
    • Authentication (Xác thực — "Bạn là ai?"): Kiểm tra username/password hoặc token thông qua authenticate(), login(), gắn vào request.user.
    • Authorization (Phân quyền — "Bạn được phép làm gì?"): Kiểm tra quyền hạn qua user.is_staff, user.is_superuser, Groups, và user.has_perm('blog.delete_post').
  • Câu 45 (Middleware — Mô hình củ hành Onion): Là các lớp bọc ngoài toàn bộ các View. Khi Request đi vào, nó đi từ trên xuống dưới qua từng Middleware (Kiểm tra bảo mật ➡️ Đọc Session ➡️ Gắn request.user ➡️ Kiểm tra CSRF); khi Response đi ra, nó đi ngược từ dưới lên trên. Ứng dụng: Ghi log thời gian xử lý API, kiểm tra JWT/CORS, Rate Limiting.
  • Câu 46 (Session vs Cookie):
    • Cookie: Lưu trữ trên trình duyệt của Client (tối đa ~4KB), gửi kèm trong mỗi HTTP request.
    • Session: Dữ liệu nhạy cảm (user_id, giỏ hàng) được lưu trên Server (Database hoặc Redis), còn trình duyệt chỉ giữ một chuỗi mã ngẫu nhiên vô nghĩa là sessionid bên trong Cookie!

2.5 API (DRF), Security & Deployment (Câu 47 – Câu 52)

Câu 47 – 52: Django REST Framework (Serializer, ViewSet)? JWT vs Session? Bảo mật? Static vs Media? Checklist Deploy?
  • Câu 47 & 48 (DRF & Serializer): Django REST Framework (DRF) là bộ công cụ chuẩn để viết RESTful API trong Django. Serializer đóng 2 vai trò:
    1. Serialization (Chiều ra): Biến đổi Django Model / QuerySet thành dữ liệu Python dict ➡️ JSON trả về cho Frontend/Mobile.
    2. Deserialization & Validation (Chiều vào): Nhận JSON từ client, kiểm tra tính hợp lệ (serializer.is_valid(), validate_<field>, validate()) và lưu xuống DB qua serializer.save().
  • Câu 49 (Token/JWT vs Session Auth): Session Auth là Stateful (Server phải tra cứu DB/Redis mỗi request, gắn chặt với Cookie nên hợp với Web SSR truyền thống). JWT (JSON Web Token) là Stateless (Payload chứa user_id, thời hạn exp và được ký bằng SECRET_KEY — Server xác thực chữ ký ngay trong RAM mà không cần query DB, truyền qua header Authorization: Bearer <token> nên cực kỳ phù hợp cho React/Vue SPA, Mobile App iOS/Android và Microservices).
  • Câu 50 (5 Lỗi Bảo Mật Phổ Biến Khi Làm Django):
    1. Để quên DEBUG = True trên Production (lộ toàn bộ biến môi trường và cấu trúc code khi có lỗi 500!).
    2. Hardcode SECRET_KEY hoặc password DB đẩy lên Git.
    3. SQL Injection: Nối chuỗi f-string trực tiếp vào Model.objects.raw(f"SELECT ... WHERE name = '{name}'") thay vì truyền tham số params=[name].
    4. XSS (Cross-Site Scripting): Dùng bừa bãi filter {{ user_input|safe }} hoặc mark_safe() tắt cơ chế auto-escape của Django.
    5. Để ALLOWED_HOSTS = ['*'] hoặc tắt CsrfViewMiddleware.
  • Câu 51 (Static Files vs Media Files):
    • Static Files (STATIC_URL, STATIC_ROOT): Là file CSS, JS, logo, icon cố định của hệ thống do lập trình viên viết. Khi deploy chạy python manage.py collectstatic để gom về 1 thư mục cho Nginx hoặc WhiteNoise/CDN phục vụ.

def is_palindrome(s: str) -> bool:
    """
    Kiểm tra chuỗi đối xứng, bỏ qua khoảng trắng và phân biệt hoa/thường.
    Độ phức tạp: Time O(N), Space O(1) nếu dùng 2 con trỏ (Two Pointers)!
    """
    # Cách 1 (Ngắn gọn Pythonic - Time O(N), Space O(N)):
    cleaned = "".join(ch.lower() for ch in s if not ch.isspace())
    return cleaned == cleaned[::-1]


def is_palindrome_two_pointers(s: str) -> bool:
    """Cách 2 (Điểm cộng phỏng vấn - Two Pointers tối ưu bộ nhớ Space O(1)):"""
    left, right = 0, len(s) - 1
    while left < right:
        while left < right and s[left].isspace():
            left += 1
        while left < right and s[right].isspace():
            right -= 1
        if s[left].lower() != s[right].lower():
            return False
        left += 1
        right -= 1
    return True

from typing import Any

def find_most_frequent(items: list[Any]) -> list[Any]:
    """
    Trả về danh sách các phần tử có số lần xuất hiện cao nhất (xử lý cả trường hợp hòa).
    - Time Complexity: O(N) (Duyệt qua list 1 lần để đếm trên Hash Table + 1 lần tìm max)
    - Space Complexity: O(K) với K là số phần tử phân biệt trong list.
    """
    if not items:
        return []

    counts: dict[Any, int] = {}
    max_count = 0

    for item in items:
        new_count = counts.get(item, 0) + 1
        counts[item] = new_count
        if new_count > max_count:
            max_count = new_count

    # Lấy tất cả phần tử đạt max_count (xử lý trường hợp hòa nhau!)
    return [item for item, count in counts.items() if count == max_count]

import time
from functools import wraps
from typing import Callable, Any

def measure_time(func: Callable) -> Callable:
    @wraps(func)  # Giữ nguyên func.__name__ và func.__doc__
    def wrapper(*args: Any, **kwargs: Any) -> Any:
        start_time = time.perf_counter()
        try:
            return func(*args, **kwargs)
        finally:
            # Đặt trong finally để kể cả hàm văng Exception vẫn đo được thời gian chạy!
            elapsed_ms = (time.perf_counter() - start_time) * 1000
            print(f"[TIMER] Hàm '{func.__name__}' chạy mất {elapsed_ms:.2f} ms")
    return wrapper

@measure_time
def heavy_computation(n: int) -> int:
    """Tính tổng bình phương."""
